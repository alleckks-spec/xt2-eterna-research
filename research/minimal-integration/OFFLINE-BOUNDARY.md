## What executed

The new actor runner uses full original constructors for main, processing/cache
and the neighboring initialization task. After original menu commit and a
borrowed original snapshot/sender caller, native queue send, scheduler receive
and the real main200 handler execute. The neighboring task receives its own
initialization and publishes its pointer natively. No host packet-copy,
sender-task-ID, profile-byte, processing-state or live-view-handle replacement
supplies this continuation. This is a stronger transport check than the
separate15-case function/phase assay, with different bounded coverage.

The initial null-pointer stop was a missing constructor in the harness and
was resolved with the original constructor. Lazy VFP uses the existing native
exception handler. Actual native table selections identify two primary RAM
pool extents, excluding the patch carriers; only missing backing for these
explicit objects was added after native identity/RW mapping checks. A separate
fixed scratch backing follows actual memset arguments. No companion context
pool or peripheral reply is fabricated. Carrier CPU writes were watched during
the selected constructors and subsequent task execution; none were observed.

These are host-preloaded, serialized two-core kernel/ELF fixtures, not reset
boot or a complete camera model. Existing menu-mode/synchronization fixtures
and borrowed caller sequencing remain. Runtime zero register defaults and
virtual-time policies are declared assumptions, not camera measurements.

## Exact remaining actor boundary

Without supplied input, native initialization reads GPIO0 input, specifically
pin0.4. High remains in the native wait loop; low continues. Its actual level
and timing are unknown. Under explicitly conditional GPIO0=0, original serial4
configuration executes. An artificial fixed-timer busy-wait was resolved using
the existing timer count model, one virtual tick per native counter read;1924
steps crossed the delays without a timer expiry. This is not elapsed-time
calibration or IRQ-delivery evidence.

The existing transfer probe supplies provisional controller empty/room flags
and stops **before the first outgoing byte completes**: serial4 SEND register,
value0. It does not answer the device. Continuing requires actual register0
read/ready/completion behavior and subsequent device responses. Existing
synthetic1234/abcd frame checks are not hardware evidence or valid substitutes
for those inputs. Capture-cache and capture profile remain0; the native
live-view-handle callback and15fc cache update were not reached.

## Memory evidence and its limit

All4096 L1 slots and used L2 mappings were enumerated after the actual
image-contained protection wrapper. Three data pages have only identity
AP7/XN mappings; the code-tail page has only identity AP7/executable mapping.
No alternate writable CPU alias exists in that current32-bit stage-1 table.
The inventory is unchanged between root return and the later PL330 boundary.
The inventory's synthetic check detects deliberately writable section aliases
and repeated large-page mappings. This does not audit future remaps, other
translation tables, physical bus aliases or DMA masters.

The continuous later startup fixture remains bounded at a PL330 request whose
source is device configuration NV,851968bytes absent from the official update
input. Its decoded destination excludes the carriers. A synthetic erased
configuration would be a different boot condition, not healthy-camera lifetime
evidence. Section2/5 cold reloads would still destroy the carriers; actual
preloaded delivery/retention remains essential. RO can turn a conflicting
native write into an abort, so protection is not ownership proof.
