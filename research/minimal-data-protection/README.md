# Минимальный Sepia→ETERNA: защита данных перед первым потребителем

2026-11-08. Промежуточный инженерный результат; цель активна. Исходники и анализ подготовлены с помощью OpenAI Codex. Никто не приглашался к испытаниям, сборки владельцам не отправлялись.

**Решение:** новый активный вариант пока не допущен к полной загрузке на камере. Для первого отдельного раннего испытания остаётся диагностический `c136d6d7…` из `xt2-delivery-probe-first-test.txt`. Его успех не будет автоматическим допуском этого варианта.

## Исправленный риск

В численных проверках хост задавал данным RO/XN. Сам `c1aee308…` этого не устанавливал: ранний native-снимок показывал для padding `0x781000…0x784000` RWX. Код в хвосте resident-секции уже имел RX. Поэтому прежние изолированные проверки не доказывали фактическую защиту данных в загрузке.

Новый вариант на существующей границе `cf8214`, до исходного вызова `cf83cc`, проверяет фиксированный ранний контекст, исходные MMU-атрибуты и сумму трёх страниц данных. Затем штатный `cf2100` устанавливает им RO/XN; результат, восстановление affinity и итоговые дескрипторы проверяются. Wrapper восстанавливает входные регистры/флаги/SP/LR и tail-call передаёт управление исходному `cf83cc`. Нового аллокатора для профиля, файлового загрузчика или перезагрузки профилей нет.

Весь дополнительный код — 1044 байта — поместился в прежнем RX-хвосте, заканчивается до `df8000`. Первоначальный вариант с общим MMU-walker не помещался и не принят; итоговая версия проверяет только закреплённый формат 4.41 и отклоняет другие атрибуты. Ранняя сумма теперь покрывает новый hook и новый код; чтобы сохранить прежние семь выровненных дескрипторов, расширен уже проверяемый resident-интервал. Проверяется 780916 байта вместо 80348. Физическое время этого чтения и watchdog ещё не измерены.

Исправлен дефект первого варианта: ошибка API больше не обходит повторную проверку контекста. Тест потери root одновременно с protect-error подтверждает отсутствие запроса питания. Прежний `96b32e2f…` не является итоговым кандидатом.

При неизвестном раннем контексте wrapper маскирует AIF и ожидает без запроса питания. При остальных проверенных отказах в допустимом раннем контексте выполняет запрос очистки только bit 0 `FFF10004`, DSB и WFE. Это не глобальная flash-защита, штатное позднее shutdown или проверенный recovery. При неизвестном контексте намеренно не делается предположение, что другое ядро не сохраняет данные.

## Что исполнено

- Ограниченный запуск нового образа с host-preload от существующего native-префикса прошёл **встроенный** wrapper → исходный `cf83cc` → возврат `cf8218`. Хост не вызывал protect вместо wrapper и не устанавливал patch во время вызова. Регистры, флаги, SP/LR на входе в исходную функцию совпали с первоначальными; affinity восстановлена; наблюдаемый расход root-стека 364 байта, остаток 544 байта. Границы проверены для собственного compiled-кода; scheduler-переходы не отождествляются с root только по SVC/current-task.
- Native `cf2100` действительно выполнил защиту через существующий двухъядерный scheduling-стенд. Итоговые три страницы AP=7/XN=1, физические адреса прежние. Остальные 253 страницы того мегабайта сохранили physical/AP/XN; cache/shareability/security-атрибуты и сохранность RO/XN после возврата оригинального вызова проверены финальным префиксом. В рассматриваемом префиксе нет CPU-записей в код/данные кандидата и входов в четыре наблюдаемых flash-writer API.
- Отдельная ранняя проверка прошла с расширенным диапазоном; изменения первого/последнего байта нового кода, нового root-перехода и expected word остановились до LED/reset без MMIO. Неизменённые старые fault-grid и численные сетки не повторялись.
- Девять отрицательных compiled-C fixtures проверяют неправильный root, исходные права, MMU-domain, последний байт защищаемых страниц, ошибку protect, ошибку восстановления affinity, ложный status=0 без изменения страниц и ошибку API вместе с утратой допустимого контекста. Штатный startup не продолжился. В этих fixtures TCB/MMU и API-ответы синтетические; возвращаемые нули служат инъекции последующих отказов, а не доказательству успешной native-защиты. Реальный успешный вызов доказан отдельным native-префиксом.
- Дополнительная проверка двух исходных low-loader branch-сегментов подтвердила: при закреплённом mode=1 по `e978` сохраняется preloaded table и пропускаются исходные transfer-ветки. Mode лежит вне штатного BSS-clear. Контрпример mode=0 дошёл до попытки copy table из flash; успех копирования не подставлялся. Между сегментами пропущены time logger/section lookups; это не непрерывное исполнение loader.

Локальные доказательства: `minimal-protected-prefix-verification.json`, `minimal-protected-failure-verification.json`, `minimal-preloaded-branch-verification.json`, `minimal-data-protection-prefix.json`. Полные вспомогательные отчёты финального запуска изолированы в `research/minimal-protected-prefix-274de1d23e82/`, прежние общие report paths восстановлены. Первый прямой одноконтекстный вызов protect не завершился за бюджет: функция переносит задачу между ядрами. Он не принят как успешный; вместо него использован существующий scheduler, без подмены результата.

## Уточнение постоянных изменений

Найден дополнительный штатный путь вне page program/sector erase: low loader при manufacturer byte `C2` вызывает конфигурацию, которая получает SR, включает WEL и передаёт `01h` с сохранённым младшим байтом SR и `85h` в старшем конфигурационном байте. Затем ждёт снятия busy и проверяет конфигурацию. Аналогичная resident-функция имеется, но прямых BL/B и literal-ссылок на неё в образе не найдено; её достижимость из startup пока не подтверждена. Наличие функции не выдано за исполнение на камере.

У документированного [Macronix MX66L1G45G J-grade](https://www.macronix.com/Lists/Datasheet/Attachments/8819/MX66L1G45G%2C%203V%2C%201Gb%2C%20v1.2.pdf) большая часть CR — volatile, TB — OTP, а часть SR — nonvolatile. Это пример поддерживаемого командного семейства, **не установленная модель flash X-T2**. Производитель описывает совместимость и различия с Micron в [AN0309](https://www.macronix.com/Lists/ApplicationNote/Attachments/1958/AN0309V1%20-%20Comparing%20Micron%20N25Q00AA%20with%20Macronix%20MX66L1G45G.pdf). Исходный opcode `61h` в ветке `20` согласуется с enhanced-volatile configuration этого семейства; физическая микросхема не идентифицирована.

Следовательно, «проверить уже установленное 85 и просто пропустить настройку» без иных условий неправильно: volatile поля могут начинать с defaults. Предполагаемая замена WREN другой командой без полного JEDEC не установлена и не добавлена. Низкий caller не проверяет возвращаемую ошибку C2-config, поэтому один подставленный error return также не является защитой. Нужно отдельно сохранить режим чтения и WEL/WIP-состояние. Код этого пути новым вариантом не изменён. Нельзя заявлять отсутствие постоянных транзакций или всех рисков для SR/OTP/калибровок.

## Что осталось

RO/XN уменьшает риск CPU-порчи/исполнения данных после проверенной границы. Это не защита от DMA, изменения таблиц страниц, неаудированных writable-алиасов, потери RAM до wrapper или неверного ROM-handoff. Сохранность через полную загрузку/реальный capture и взаимодействие с поздними писателями ещё не проверены. Смысл AP/XN зависит от Client-domain и состояния MMU; эти предпосылки проверяются кодом, согласно [ARMv7 Architecture Reference Manual](https://documentation-service.arm.com/static/5f8daeb7f86e16515cdb8c4e).

Первое необходимое аппаратное наблюдение остаётся прежним ранним диагностическим тестом доставки/питания/обычного возврата. Для разбора специфичных flash-настроек нужен полный JEDEC/подтверждённая маркировка либо существующая достоверная трасса штатной инициализации. Публичный каталог оставляет JEDEC/geometry неизвестными; просмотренные первичные публичные материалы их не установили. Не требуется разбирать камеру или вслепую писать SPI/MMIO: при отсутствии готовых данных сначала нужен отдельный план чтения/наблюдения на штатной камере. После этих данных — поздний checkpoint сохранности и оценка ограниченного запуска активного варианта. Цель не объявлена выполненной.

## Source dependencies

Place these original sources in the original workspace `scripts/` layout. They require private pinned c1 minimal/stock images and local firmware/research inputs, the existing native startup/scheduling harness, Clang/ARM LLD, pyelftools and Unicorn TCI. The public repository alone is not a standalone build. The original guard helper is in minimal-hardware-candidate, and branch/hash helpers are in delivery-probe. No firmware, donor tables, raw manifest, disassembly or private reports are included.

Build locally with `.venv/bin/python scripts/build_xt2_minimal_protected.py`; verify using `LIBUNICORN_PATH="$PWD/.toolchains/unicorn-tci" UC_IGNORE_REG_BREAK=1 .venv/bin/python scripts/verify_xt2_minimal_protected_prefix.py` and the corresponding failure verifier. This host's sandbox denies the cache-line sysctl required by Unicorn, so bounded native checks ran outside it without camera/network access.

The published builder derives the original root BL preimage from its addresses rather than carrying a copied instruction word. With private inputs supplied, its output was compared byte-for-byte to the exact final image; this does not make the public directory a complete build package.
